--Summary Comment: This T-SQL script contains algorithms that can be used to design a very efficient storage space, and network transmission, string data format, for table/matrix/grid data structures... The Obsidian Compound Object String (OCOS) data format, is ultimately, a very size efficient storage option. The downside is that it would typically lead to more compute demand when later used (due to the need to unwrap the string into a grid), and as a direct consequence, is less suited to latency sensitive usecases... Obviously wrapping would also carry compute-latency penalties.

--Nota Benes:
--Before feeding data into the following algorithms, you must make sure that it does not contain row or column/cell delimiter string patterns, within the actual data values of interest (that is, within useable data values that are not intended for metadata structural purposes)...

If you are successful here, please make sure you do the clever thing, and only store one copy of any common stem string pattern for each partition, and then you would simply store this in a variable which could be joined to all rows on a partition by parition basis, in parallel, when unwrapping from string to grid. I think I would call this the Obsidian Parquet format (On a related topic, also, there are other things for each partition that could be stored, such as basic statistics {although this may be unpalatable for purists who simply want quickest performance})... I'd just like to also mention here, that you would want to store each base table partition (all the members, or rows and columns, which share some sort of common 'stem or characteristic') in a single Obsidian Compound Object String (OCOS), such that you would have multiple OCOSs, each one corresponding to a partition and its members, stored on an overall partition map which is stored in place of the tradtional standard base table, which would otherwise simply have had a basic rows mapped against columns grid... Each of the Obsidian Compound Object String (OCOS) values should be stored alongside their partition 'anchor' value, such that you have the partition index in the first column, the 'anchor or stem' value in the second column, and the actual data payload in the Obsidian Compound Object String (OCOS) value, in the third column (I suppose other columns could be stored, like as mentioned statistics and other cached partition aggregates)...
--Please be aware, I suppose, that you could store a header row for other useful associated data, such as column data types, or maybe even basic things like business logic variables etc_...
--BTW, this data storage and transmission OCOS format, is almost certainly always going to be more size and speed efficient than the same data stored in JSON data format... The main reason, is that with OCOS, we don't keep adding unnecessary labels for each data field, but simply state each column name, once at the left of the payload string, in one of the  headers (obviously this is expecting symmetric data value structure, which should nearly always be the case when working with table data in a SQL-engine or similar, for example python data frames in Pandas or NumPy).
--I feel it pertinent for me to draw your attention to the following here... That it would be right to prefer to use a genric data type like Varchar(Max) for column definitions during all wrap and unwrap transformations, because it means that you can simply ingest most if not any data, even after underlying data model changes in other integrated systems and apps, which could othereise cause clashing data types which would be incompatible with your database and therefore cause a pipeline errors. With Varchar(Max) this problem should be eliminated (almost entirely), as it cam store any combnstion of ASCII characters, which should cover even most custom data types... Please simply remember like I have said, to Cast() or Convert() before using in critical downstream transformations after unwrapping...
--Finally, I would say that the ideal uses for these compound data format algorithms, are: 1. Long term storage; 2. Infrequently accessed storage; 3. Transfer of data between apps or systems; and 4. Transfer of data across private local networks, all the way up to public global networks.
