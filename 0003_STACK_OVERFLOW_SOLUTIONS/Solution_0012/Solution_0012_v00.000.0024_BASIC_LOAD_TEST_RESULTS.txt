Took an executive decision to switch the serial algorithm test, to emulate general programming language array index-based slicing operation behaviour, in order to properly compare to SQL Server set-based parallelism, without exponentially deprecating serial performance purely because of missing SQL Server features and idiosyncrasies, that unnecessarily slow things down for certain computation design patterns... Infact, upon further load testing, I have realised, that because SQL Server requires Where clauses that scan many rows in order to locate a specific row, it is not a suitable load test... We would need to access two features in T-SQL, in order to make this comparison work properly... A force row order command, in order to assume the order according to the values as they are stored on hard drive, and also we would need access to array index-based slicing operators, in order to rapidly intersect with the table for serial updates, either a row at a time, or a cell at a time... Stopping serial load testing here... Carrying on with just parallel load testing!
