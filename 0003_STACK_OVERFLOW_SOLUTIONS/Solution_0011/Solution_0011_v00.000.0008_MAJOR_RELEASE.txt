--GUIDANCE:
--This algorithm implements an example technical approach, which should be usable, with augmentations/customisations, in order to dynamically handle any hierarchical rollup aggregation, without needing to handcrank sourcecode group references, because the hierarchy and it's partitions and branch points, are built from a simple table, which can hold data which has been automatically generated by any kind of business logic computation... I don't think that this is currently possible in core T-SQL... Might be though, as I haven't actually checked the online documentation properly...
--Please be aware, that it is possible to feed aggregates into the rollup hierarchy at any branch level (new functionality), as well as at the leaf level (existing core SQL Server functionality)... Please make sure you understand the ramifications of this before use!!!


--INPUTS:
Declare @Partitioned_Branching_Hierarchy_Auto_Mapper Table ([Partition] BIgint, [Order] Bigint, [Location] Varchar(Max))
Insert Into @Partitioned_Branching_Hierarchy_Auto_Mapper ([Partition], [Order], [Location])
Values
--Rules For This @Auto_Referenced_Table table...
--1. Use the [Partition] column, to group all members of a particular partition (or branch) within a particular hierarchy, such that aggregation will flow up through this partition (or branch) to the ultimate ancestor node...
--2. Use the [Order] column, to sequence members of a hierarchy within a partition (or branch), making sure that there are no duplicated [Order] indexes......
--3. Use [Order] column, in order to define the branching points of the hierarchy within each partition...
--4. Nota Bene 0001: If a particular member within a hierarchy partition, is actually at a higher level in the hierarchy, than another member within the same hierarchy partition (or branch), then it should have a lower [Order] column value...
--5. Nota Bene 0002: Don't worry about [Order] column value specifics within the same hierarchy partition (or branch) and hierarchy level combination, other than uniqueness, and no index gaps...
--6. Please make sure that the [Order] column index values are all unique wherever possible, otherwise you may get wanted/unwanted duplicate aggregations... The [Location] column is allowed to have duplicate values though, so long as the associated [Partition] and [Order] columns contain unique values across the duplicate group...
--Noat Bene 0001: It may take you some time, in order to get your head around the non-intuitive way that this algorithm makes use of the order column, in order to define hierarchy branching... Esentially, when rolling up an aggregate to a particular node in the hierarchy, we look for all higher order nodes within the same partition, and then simply apply an Aggregate() function on the group...

--SOLUTION:
Declare @Resolution_Table Table ([Partition] Bigint, [Order] Bigint, [Location] Varchar(Max), [Aggregate_Value] Bigint) --The column data type definition of the [Aggregate_Value] declaration here, must be kept in synch with the corresponding column data type definition above, on the @Multi_Level_Branch_and_Leaf_Aggregateable_Data table...
Insert Into @Resolution_Table ([Partition], [Order], [Location], [Aggregate_Value])
Select
	A.[Partition] As [Partition],
	A.[Order] As [Order],
	A.[Location] As [Location],
	C.[Aggregate_Value] As [Aggregate_Value]
From @Partitioned_Branching_Hierarchy_Auto_Mapper A
Left Join @Partitioned_Branching_Hierarchy_Auto_Mapper B
	On (B.[Partition] = A.[Partition] And B.[Order] >= A.[Order])
Left Join @Multi_Level_Branch_and_Leaf_Aggregateable_Data C
	On (C.[Partition] = B.[Partition] And C.[Order] = B.[Order])
--We use [Partition] column and [Order] column equality checking, in order to be able to deal differently with situations where your data may have [Location] column value duplicates...


--OUTPUT:
Select
	Min([Location]) As [Location], --I'd rather just have access to an aggregate that would simply pick Any_Value()... It would be more performant in the core SQL Server engine...
	Sum([Aggregate_Value]) As [Aggregate_Value]
From @Resolution_Table
Group By [Partition], [Order]
--Order By [Order] Asc --It is not necessary to use this Order By command... It can seriously slow down your algorithm compute execution time... Here it is only intended for testing purposes...
