--Is this simply a design anti-pattern? --> Well yes, when thinking in terms of optimal compute speed, but no, when thinking of ease-of-engineering speed...
--Is this even a worthwhile usecase? --> Well, I certainly enjoyed implementing it, and I'm sure that some few others will enjoy utilising it...
--Is the comparative performance to native syntax, a runaway disaster, as data volumes expand? --> Not sure really, as I haven't tested this myself... Can someone else in a role of authority, please do the honours here, with regards to this...
--Is there anything else that people need to be aware of, with regards to matters more technical? --> Well yes, there is... Because we are approaching filtering of table at runtime only, via dynamic T-SQL execution, there are a few major drawbacks... 1. Caching is incompatible, both for query execution plans, and for output results; 2. Table variables massively restrict functionality to a mere few million rows, and so you will need to adjust this yourself, if you wish to use this algorithm and its design pattern for larger volumes of data, by swapping in temp tables or standard tables, wherever table variables are currently used here in query; 3. Please bare in mind, that no matter what you do - because any table must be fed into the Execute sp_executesql command as a duplicate - this will always lead to unecessary compute speed and storage penalties... Microsoft could implement dynamic SQL execution in such a way that this problem could be avoided, but good luck convincing them!!!

Declare @Predicate_Group_ID_0001 As Bigint
Set @Predicate_Group_ID_0001 = 2 --Please use this variable assignation wisely... It corresponds to the set or group predicates that you want to apply to a given dynamic filter instance... It is very powerful in shaping the usage of the overall algorithm... Essentially, you use it to map different predicate sets, to different instances of use of dynamic predicates on various tables within the query... Further up in the sourcecode, you populate your super table of all or as many filter predicates that are of use to you in the current query... Each predicate command row, comes with a Bigint Predicate_Group_ID value in the [Predicate_Group_ID] column, and so it allows you to very quickly and easily assign different predicate sets or groups to different instances of the application of this dynamic filter predicates design pattern, on different tables within the same query, without having to duplicate effort... You simply use one superset of predicates, and filter it, using this assigned variable @Predicate_Group_ID, which then subsequently dynamically applies different predicate sets to the different tables of interest, at different points throughout the query... A little wordy, but were dealing with a complex feature here... Please feel free to play around and therefore understand how to use it properly...

Declare @Dynamic_SQL_Command_0001 As Nvarchar(Max)
Set @Dynamic_SQL_Command_0001 =
N'
Select
	[Order] As [Order],
	[Data_Group_ID] As [Data_Group_ID],
	[Date_Value] As [Date_Value],
	[String_Value] As [String_Value],
	[Number_Value] As [Number_Value]
From @Data_Table
Where '
	+
	(Select String_Agg(([Alpha_Predicate] + [Predicate_Logical_Or_Comparison_Operator] + [Beta_Predicate]), ' ') Within Group (Order By [Order] Asc) From @Predicate_Table Where [Predicate_Group_ID] = @Predicate_Group_ID_0001)

Execute sp_executesql @Dynamic_SQL_Command_0001,
N'
@Data_Table [dbo].[Data_Table] Readonly,
@Predicate_Table [dbo].[Predicate_Table] Readonly,
@Predicate_Group_ID Bigint
',
@Data_Table = @Data_Table,
@Predicate_Table = @Predicate_Table,
@Predicate_Group_ID = @Predicate_Group_ID_0001
